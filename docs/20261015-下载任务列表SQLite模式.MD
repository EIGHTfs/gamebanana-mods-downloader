# 下载任务列表 SQLite 模式（gbmd）

- 日期：2026-10-15
- 范围：**只改下载任务列表的落盘**（`json/download_task.json`）。
- 本次不做：索引 `json/index/`、任务导出导入（`/api/task/export|import` 维持 JSON）、前端、任务数据结构与状态机、
  共用模板件 `server/store/state-store.js`。
- 另含一项：**gbmd / iwara 启动日志打印 Node 版本**（走模板下发件 `templates/js/core/app.js`，两仓共用同一处）。

## 一、为什么改（全部本机/部署端实测）

部署端 `json/download_task.json` 峰值 **3.6 万项 / 34.3MB**（2026-10-11 现场记录，见
`server/routes/download.js` 的注释）。该文件是**整份文档**：任一条状态变化都触发
`stringify 全量 + 写盘 + rename`，节流窗口（现 10s）内主线程被占满。

实测对照（同机）：

| 操作 | 当前实现 | `node:sqlite` |
|---|---|---|
| 单条状态更新 | 整份 stringify + 写盘（12.7MB 时 stringify ≈80ms、写盘 ≈21ms） | **UPDATE 0.377ms** |
| 单条删除 | 整份重写 | **DELETE 0.991ms** |
| 单点查询（7 万行中） | 全量载入后内存查找 | **0.012ms** |
| 全量载入 / 建库 | JSONL 读+解析 285ms | 单事务插入 70k 条 300ms（**持平**） |

结论：**收益只来自「行级增量写」**，不来自「载入更快」。因此本方案的关键是
**只写变化的行**，而不是把 JSON 换成一个 SQLite 文件（后者只换来 IO 方式变化，收益接近于零）。

**端到端对照**（含「找出哪一行变了」的差异扫描与提交开销，3.6 万项实测）：

| 场景 | 当前 JSON 整份重写 | SQLite 增量写 |
|---|---|---|
| 改 1 条后落盘（3 万条） | 121ms | **26ms（4.7×）** |
| 改 1 条后落盘（3.6 万条，真实峰值） | 134ms | **30ms（4.5×）** |
| 首次落盘（写满 3.6 万项） | 155ms | 285ms（每批一次的一次性成本） |

> 表中「UPDATE 0.377ms」是纯 SQL 时间；端到端还要加上差异扫描（约 20ms，6 万个行比较）
> 与提交开销。落盘用 WAL + `synchronous=NORMAL`（任务列表是临时状态，崩溃最多丢最后几秒进度，
> 不损坏库），换来每次提交不再强制 fsync。

## 二、怎么做

### 2.1 新增 gbmd 自有模块 `server/lib/task-sqlite-store.js`

- 依赖 **Node 内置 `node:sqlite`**（零依赖项目的唯一可行路径；`better-sqlite3` 等 npm 包不可用）。
- 对外接口与现有写入器**完全一致**：`save() / flush() / cancel() / stats / _hasPending()`。
- 表结构（每行存该元素的 JSON 文本，**保持与旧 JSON 逐字段等价**，不做字段拆解）：

```
task_meta(k TEXT PRIMARY KEY, v TEXT)          标量与数组字段
task_items(idx INTEGER PRIMARY KEY, v TEXT)    items[] 按下标
task_results(idx INTEGER PRIMARY KEY, v TEXT)  resultsMap 按下标
```

- **只写变化的行**：落盘前与上一份缓存做**扁平字段逐项比较**（`items`/`resultsMap` 的元素都是扁平标量，
  约 12 字段 × 1.3 万行 ≈ 1–2ms），仅变化行做 UPSERT、消失行做 DELETE；**不做整份 stringify**
  （那正是当前代价的来源）。单次落盘在一个事务里提交。

### 2.2 接入 `server/lib/download-task-store.js`（gbmd 自有）

- 运行期探测 `node:sqlite`：可用 → SQLite 后端；**不可用（Node < 22.5）→ 回落现有 JSON 写入器**。
- **读写与切换规则（2026-10-15 定，自动切库）**：
  · 旧 `download_task.json` 那批**还有未完成项**（`status=running/preparing`，或仍有 item 没有结果）
    ⇒ 读写都继续走 JSON（不打断正在跑的批次）
  · 那批**已全部下完** ⇒ **自动切库**：先把当前状态完整写进 SQLite，确认无错后才把旧 json
    退休进同目录 `.trash`（可恢复），再改用 SQLite
  · 没有旧 json ⇒ 直接用 SQLite
  · 切换在每次 `save/flush` 时**惰性判定** ⇒ **不需要重启、不需要迁移脚本**；`backend=json` 可强制不切
  · 状态还没恢复出来时不切（此刻落库会把空状态写进去 = 清空队列）；落库失败则不退休旧文件，下次再试
- 启动日志打印**实际生效的存储模式**（含选择原因），便于现场判断走的是哪条路。

### 2.3 不做迁移脚本（依据）

下载列表是**临时状态**：一批任务全部下载完成后整份销毁，不存在需要长期搬运的历史数据。
唯一要覆盖的场景是「切到 SQLite 时手上正好有一批在跑」——由 2.2 的**自动切库**解决：
那批没下完就继续用 json；下完的第一次落盘就把状态完整写进库、把旧 json 退休进 `.trash` 并切到 SQLite。
⇒ 不需要任何人工执行的迁移脚本，也没有启动期的批量转换。

### 2.4 启动打印 Node 版本（模板下发件，两仓共用）

`templates/js/core/app.js` 的服务启动日志增加一行 `Node <process.version>`；
组装下发后 gbmd 与 iwara 同时生效。

## 三、对外契约（必须逐字段不变）

`GET /api/task`（摘要）、`GET /api/task/items`（分页）、`GET /api/task/done`、
暂停/恢复/停止/重试失败/并发/恢复模式 —— 响应体与改造前**逐字段一致**（用等价性断言钉死）。

## 四、验收

1. 峰值规模（合成 3.6 万项）下，改 1 条后的**增量落盘耗时 134ms → 30ms（4.5×）**；
   首次落盘 285ms 属每批一次的一次性成本。（原定「< 5ms」未达成，按实测修正为 30ms 量级。）
2. 同一内存态分别经 JSON 后端与 SQLite 后端落盘再读回，**逐字段相等**。
3. 伪造 `require("node:sqlite")` 抛错 ⇒ **自动回落 JSON 路径**且功能不降级。
4. 全量 `node --test` 保持绿；两仓 `setup.sh --check` 清单两端一致。
5. 部署端启动日志出现 Node 版本与存储模式；前端任务页渲染正常。

## 五、风险与边界

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| `node:sqlite` 实验性 API 变更 | 中 | 升级 Node 后不兼容 | 只用最基础的 DatabaseSync/exec/prepare；单点封装在一个模块内 |
| 老 Node 无 `node:sqlite` | 高（实测 v20.19.5 / v14.21.1 都没有） | 启动即崩 | 运行期探测 + JSON 回落 |
| WAL 侧车文件 `-wal/-shm` | 高 | 备份/导出拿到半截数据 | 导出/备份前 `PRAGMA wal_checkpoint(TRUNCATE)`；清单登记三个文件 |
| 迁移写坏队列 | 低 | 下载队列丢失 | 默认 dry-run + 回读校验 + 旧文件进 `.trash` |
| 同一目录多进程打开 | 低 | 写入冲突 | 项目单实例运行；打开失败即回落 JSON |

边界条件：① 首次启动无任何数据（`task` 为 `null`）② `.db` 存在但为空表 ③ 旧 `.json` 不存在 ④
`.db` 被外部删除或损坏 ⑤ 迁移时 `.db` 已存在。
