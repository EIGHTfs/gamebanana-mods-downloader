# 索引 JSONL 改造（gbmd）

- 日期：2026-10-15
- 范围：`json/index/` 下索引的**存储格式**与读层。**不含**写入/批量落盘策略、不含在线搜索。
- 状态：已实现并部署端验收

## 一、为什么改

`json/index/<游戏名>.json` 原为整文件 JSON（2 空格缩进）。部署端实测规模：**12 个文件 / 93MB**，
最大单个 **Genshin 26.6MB（71,749 条记录**：gb 9,017 / local 21,129 / name 41,603）。

实测单文件代价（对真实 26.6MB 索引取样）：

| 操作 | 耗时 |
|---|---|
| 读盘 | 199.5 ms |
| `JSON.parse` | 171.5 ms |
| `JSON.stringify(obj, null, 2)` | 171.6 ms |
| JSONL 体积对比 | 26.19MB → **22.78MB（-13.0%）** |
| JSONL 冷载入（读盘 + 逐行 parse 71,750 行） | 199.5 + 182.5 = **382 ms**（原 371 ms，**持平**）|

结论：**收益不是「更快」**（冷载入持平、体积只降 13%），而是
① 格式与 iwara 统一；② 具备**追加**能力（后续增量场景可用）；③ 单行损坏不再毁掉整个索引。

> 附：批量下载路径原先「每个 mod 目录写一次 15–26MB 索引」的问题，已在 2026-10-12 由
> `deferSave + dirtyGames + flushDirtyGames` 修掉（`server/lib/hash-index.js` 内有注释记录），
> 所以本次**没有**重做写入策略。

## 二、怎么改

### 格式（记录模型，与业务无关）

首行 meta + 每行一条记录：

```jsonl
{"_":"meta","schema":2,"game":"Genshin Impact"}
{"t":"gb","k":"b9ba5fd3…","v":{"modId":"588605","fileName":"jam_bra.zip","gbMd5":"b9ba5fd3…"}}
{"t":"local","k":"b9ba5fd3…","v":{"modDir":"…","file":"jam_bra.zip","kind":"file"}}
{"t":"name","k":"jam_bra.zip","v":{"modId":"588605","kind":"file"}}
```

- `t` ∈ `gb` / `local` / `name`（对应原三段 map）
- 同段同键重复出现 ⇒ **后写覆盖先写**（last-wins），与「整文件重写」语义等价
- 坏行跳过并计数，不因一行损坏丢掉整个索引

### 代码落点

| 位置 | 改动 |
|---|---|
| `server/lib/jsonl-store.js`（**模板下发件**） | 新增：双读、O(1) 追加、原子全量重写、坏行容错、迁移驱动 `migrateDir` |
| `scripts/migrate-json-index-to-jsonl.cjs`（**模板下发件**） | 新增：独立迁移脚本（CLI + `require` 双入口），按 profile 提供业务拆合 |
| `server/lib/hash-index.js` | `loadGameIndexByBase()` 双读；`saveGameFile()` 写 JSONL；`load()` 兼容两种扩展名并在读取前同步迁移；`migrateLegacy()` 的「已有新格式」判定同时认 `.jsonl` |
| `server/app.js` 启动链 | 无需改动 —— `hash-index.load()` 本身就是启动加载入口 |
| `test/index-jsonl-parity.test.cjs` | 新增 5 例：迁移发生 / 前后等价 / 结构等价 / 幂等 / 只有 jsonl 时可用 |

**查询函数（`queryByHash` / `searchGb`）一行未改**：双读把两种格式都还原成同样的三段 Map，上层无感。

### 为什么迁移必须「同步、且在读取之前」

若异步执行：迁移期间新落的 mod 会先建出一个**只含新记录**的 `.jsonl`；迁移脚本见目标 `.jsonl`
已存在即跳过 ⇒ 下次加载以 `.jsonl` 为准 ⇒ **旧索引整份丢失**。同步执行没有这个窗口。

## 三、迁移纪律

```
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd            # 预演（默认）
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd --apply    # 执行
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd --apply --verify full
```

- **默认预演**：不加 `--apply` 只出计划，不动盘
- **幂等**：目标 `.jsonl` 已存在则跳过，绝不覆盖
- **可回滚**：旧 `.json` 移入 `json/index/.trash/<时间戳>-<原名>`
- **自校验**：转换后立即回读校验记录数；`--verify full` 另做对象级等价比对（键序无关的稳定序列化）。
  校验不过则**保留旧文件**并记入 `errors`，不改动现场
- 启动时由 `hash-index.load()` 同步调用（`dryRun:false`），失败只告警、不阻塞启动

## 四、验收结果（部署端实测）

- 部署端 `json/index/` 迁移前已整包备份到 `json/.trash/pre-jsonl-<时间戳>.tar.gz`（8.0MB）
- 单元测试 `test/index-jsonl-parity.test.cjs` 5/5
- 全量 `node --test` 121/121（105 基线 + 11 共享单测 + 5 本项）
- 组装一致性：`bash bench-template/setup.sh --to assemble.json --check` → 清单两端一致

## 五、与模板的关系

`jsonl-store.js` 与迁移脚本是**模板下发件**（`templates/js/server/lib/` + `templates/tools/`），
两仓共用同一份实现，改动必须落在模板侧再组装。共享单测放在 `templates/_downloader/test/`，两仓同步。

## 六、已知边界

- 追加会产生同键重复行（重下/更新同一 mod）；载入时若重复行超过实时键数 1.5 倍会**自动压缩**一次
  （用内存里的 Map 全量重写，结果与原实现逐键一致）
- 本次未改任何查询/搜索逻辑，也未改在线搜索
- `json/index/` 整目录在 `.gitignore` 中，`.jsonl` 同样不入库
