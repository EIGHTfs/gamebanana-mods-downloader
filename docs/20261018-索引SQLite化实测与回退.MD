# 索引 SQLite 化：实测结论与回退（2026-10-18）

## 一、背景与结论

把 `json/index/`（HTML 反查索引）从 JSONL 换成 SQLite，动机是「增量并入只写变化的行，
不必重写整个游戏索引文件」。**正确性已验证通过**，但**实测性能是退化** ⇒ **已回退为 JSONL 优先**。

- SQLite 代码保留在 `server/lib/index-store.js`，默认不启用；要试设 `GBMD_INDEX_BACKEND=sqlite`。
- 回退点：`index-store.js` 的 `sqliteEnabled()`（默认 JSONL）与 `readIndex` / `writeIndexAtomic` / `listBases` 的读取顺序。

## 二、实测数据（双臂同机、同一份数据）

复跑命令（任何机器可跑，不需要真实索引）：

```bash
node scripts/bench-index-store.cjs --synthetic 83000  --bases 12 --iters 5   # ≈24.9 万条
node scripts/bench-index-store.cjs --synthetic 250000 --bases 12 --iters 3   # ≈75 万条
```

| 指标 | 24.9 万条 / 12 base（20.7k/base） | 75 万条 / 12 base（62.5k/base） |
|---|---|---|
| ① 启动加载 `load()` | JSONL **673ms** ／ SQLite 1.09s ⇒ **0.62×** | JSONL **2.37s** ／ SQLite 4.71s ⇒ **0.50×** |
| ② 单游戏增量写（改 1 条） | JSONL 35.1ms ／ SQLite **28.7ms** ⇒ 1.22× | JSONL 242ms ／ SQLite **212ms** ⇒ 1.14× |
| ③ 全库增量写（各改 1 条） | JSONL **353ms** ／ SQLite 385ms ⇒ 0.92× | JSONL **2.47s** ／ SQLite 2.55s ⇒ 0.97× |
| ④ 落盘体积 | JSONL 48.5MB ／ SQLite 56.5MB + WAL 20.9MB | JSONL 146.7MB ／ SQLite 187.4MB + WAL 31.3MB |

读法：写入看 `min`/`p50`，`avg` 会被 WAL 自动 checkpoint 的尖峰带偏（实测同一操作 min 109ms、avg 666ms）。

## 三、根因

1. **成本在序列化，不在文件写**：调用方（`hash-index.saveGameFile`）每次都传**全量 records**，
   `mapToRecords` + 逐条 `JSON.stringify` 是两份后端都要付的固定成本；
   JSONL 的「写整个文件」落到页缓存近乎免费，SQLite 省下的 I/O 抵不过它新增的「行 → 对象」反序列化。
2. **载入更贵**：`readIndex` 从库读要物化行对象 + 逐行 `JSON.parse`，而 JSONL 只是切行 + `JSON.parse`。
   启动加载是**每次启动都付**的固定成本 ⇒ 这一项退化的权重最高。
3. **体积更大**：行存的是值 JSON 文本，外加 `(base, sec, k)` 主键索引，比按行紧凑排布的 JSONL 更大；WAL 是额外开销。

## 四、与「任务列表 SQLite 化」的对比（同样是换库，结论相反）

| | 下载任务列表 | HTML 反查索引 |
|---|---|---|
| 数据规模 | 万级（峰值 3.6 万项） | 十万级（24.7 万条 / 76.9MB） |
| 写入形态 | **小而频繁**（每个文件状态变化都落盘） | **大而整份**（每游戏文件整体重写） |
| 载入权重 | 可忽略 | **每次启动全量载入，权重最高** |
| 实测 | 增量落盘 134ms → **30ms（4.5×）** | 启动加载 **慢 1.6–2×**，写入打平 |
| 结论 | **换库划算** | **不划算，回退** |

⇒ 判据：**「写入频繁且单次小、载入不重要」才适合换库**；「整份重写、启动要全量载入」不适合。

## 五、如果以后还想要索引的写放大收益

需要**接口层改造**，而不是换存储后端：

- 让 `saveGameFile` / `ingestModDir` 只把**变化的 key**（`{sec, k, v}` 列表）交给存储层，
  避免全量 `mapToRecords` + 全量 `stringify`；
- 存储层按 key 增量落盘（JSONL 用「追加 + 定期压缩」，或 SQLite 只 UPSERT 传入的 key）；
- 验收：用 `scripts/bench-index-store.cjs` 同一口径复测，且 `test/hash-index-baseline.test.cjs`
  的逐字段等价基线必须保持通过。

## 六、保留的东西

- `server/lib/index-store.js`：SQLite 后端 + 行级差异缓存 + 回落；默认不启用。
- `scripts/migrate-index-jsonl-to-sqlite.cjs`：JSONL → SQLite 一次性迁移（预演/apply/verify，支持 `--base`）。
- `scripts/bench-index-store.cjs`：双臂性能对比（合成数据 / 真实索引两种来源）。
- `test/index-store.test.cjs`：SQLite 后端等价性、行级增量、以及「默认走 JSONL」的回归断言。
