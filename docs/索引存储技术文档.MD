# 索引存储技术文档

> 游戏索引（`json/index/`）的存储格式、读写层、后端选择、迁移与排查。

- 适用范围：`json/index/` 下**游戏索引**的存储格式、读层、写层、后端选择、迁移与排查
- 不适用：查询/搜索业务逻辑、导出导入接口契约、下载任务列表存储（那是另一套 `task-sqlite-store.js`）
- 当前状态：**JSONL 优先**，SQLite 仅在显式开关下启用

---

## 一、分层结构

理解这套实现的关键是它只分三层，而且**每层只认一个数据结构**。

```
业务层   server/lib/hash-index.js（601 行）
         · 业务对象 ⇄ 记录：mapToRecords() / 三段 Map
         · 启动加载：load() → loadGameIndexByBase() → loadGameFile()
         · 增量落盘：saveGameFile() / mergeAll() / migrateLegacy()
              ↓ 只调用两个入口，不关心底层是文件还是库
存储层   server/lib/index-store.js（335 行）
         · 后端选择与回落（默认 JSONL；SQLite 需 GBMD_INDEX_BACKEND=sqlite）
              ↓
         server/lib/jsonl-store.js（365 行）
         · JSONL 读写、原子替换、坏行容错、JSON↔JSONL 双读、迁移驱动
```

**唯一契约**：`readIndex(fileBase)` 恒返回

```js
{ format, file, meta, records, badLines, json, bytes }
```

`writeIndexAtomic(fileBase, meta, records)` 恒返回 `{ ok, file, bytes? }`。
上层只吃这一份结构 ⇒ 换后端时业务层零改动（这也是当初敢试 SQLite 的前提）。

## 二、数据格式

### 2.1 文件布局

```
json/index/
├── <游戏名>.jsonl          ← 当前格式
├── <游戏名>.json           ← 旧格式，仍可读（双读）
├── index.db                ← SQLite 后端（仅显式开关时产生）
└── .trash/<时间戳>-<原名>   ← 迁移/清理的回收站
```

一个游戏一个文件（不是一个大索引）。名字来自 `gameIndexBase()`，非法字符由 `sanitizeGameName()` 处理。

### 2.2 记录模型（与业务无关）

首行 meta + 每行一条记录，行内是紧凑 JSON：

```jsonl
{"_":"meta","schema":2,"game":"Genshin Impact"}
{"t":"gb","k":"b9ba5fd3…","v":{"modId":"588605","fileName":"jam_bra.zip","gbMd5":"b9ba5fd3…"}}
{"t":"local","k":"b9ba5fd3…","v":{"modDir":"…","file":"jam_bra.zip","kind":"file"}}
{"t":"name","k":"jam_bra.zip","v":{"modId":"588605","kind":"file"}}
```

- `t` ∈ `gb` / `local` / `name`，对应内存里的三段 Map（`gbIndex` / `localIndex` / `nameIndex`）
- 另有 `stemIndex` 由 `name` 段派生，不落盘
- **同段同键重复 ⇒ last-wins**，与「整文件重写」语义等价
- 坏行跳过并累加 `badLines`，**不因一行损坏丢掉整个索引**

## 三、读路径（一次启动加载的完整生命周期）

1. `server/app.js` 启动 → `hash-index.load()`（这就是启动加载入口，无需额外挂载）
2. **读取前同步执行一次性迁移**（`migrateIndexToJsonl`，幂等；原因见第五节）
3. `index-store.readIndex(base)`：
   - 显式开启 SQLite ⇒ 先读库
   - 否则 **文件优先**：`.jsonl` → 旧 `.json`
   - 文件不存在（历史上被归档过）才回头试库
4. 记录 → 三段 Map（`mergeInto` / `mergeAll` 把各游戏合并进全局 Map）
5. 查询函数 `queryByHash` / `searchGb` **一行未改** —— 双读把两种格式还原成同样的 Map，上层无感

---

## 四、写路径

```
saveGameFile(game, g)
  → mapToRecords(g)                    // Map → 记录数组（这一步是两份后端都要付的成本）
  → index-store.writeIndexAtomic()     // 后端分叉点
```

- **JSONL**：原子全量重写（同目录临时文件 + rename），落盘即整份
- **SQLite**（仅显式开关）：行级 UPSERT，配合模块级 `treeCache` 记忆上次快照以便算差异
- 批量下载路径不再「每个 mod 目录写一次整份索引」——已在 2026-10-12 由
  `deferSave + dirtyGames + flushDirtyGames` 收敛（`hash-index.js` 内有注释记录）

> ⚠️ 当前实现「一次写入仍是全量」：存储层拿不到「哪些 key 变了」。这正是第七节说的优化方向。

## 五、迁移纪律（所有迁移共用同一套规矩）

**必须同步、且在读取之前**执行。若异步：

> 迁移期间新落的 mod 会先建出一个**只含新记录**的 `.jsonl`；迁移脚本见目标已存在即跳过
> ⇒ 下次加载以 `.jsonl` 为准 ⇒ **旧索引整份丢失**。

标准命令：

```bash
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd            # 预演（默认，不动盘）
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd --apply    # 执行
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile gbmd --apply --verify full
```

四条特性：

- **默认预演**：不加 `--apply` 只出计划
- **幂等**：目标已存在则跳过，绝不覆盖
- **可回滚**：旧文件移入 `json/index/.trash/<时间戳>-<原名>`
- **自校验**：转换后立即回读校验记录数；`--verify full` 另做对象级等价比对（键序无关的稳定序列化）。
  校验不过则**保留旧文件**并记入 `errors`，不动现场

启动时由 `load()` 同步调用（`dryRun:false`），失败只告警、**不阻塞启动**。

## 六、为什么是 JSONL，而不是 SQLite

### 6.1 JSONL 改造的收益（2026-10-15）

原为整文件缩进 JSON（2 空格）。部署端实测规模：**12 个文件 / 93MB**，最大单文件
**Genshin 26.6MB / 71,749 条**（gb 9,017 / local 21,129 / name 41,603）。

| 操作（对真实 26.6MB 索引取样） | 耗时 |
|---|---|
| 读盘 | 199.5 ms |
| `JSON.parse` | 171.5 ms |
| `JSON.stringify(obj, null, 2)` | 171.6 ms |
| 体积 | 26.19MB → **22.78MB（-13.0%）** |
| JSONL 冷载入（读盘 + 逐行 parse 71,750 行） | 199.5 + 182.5 = **382 ms**（原 371 ms，**持平**）|

⇒ **收益不是「更快」**，而是：① 具备追加能力 ② 去掉缩进、体积更小 ③ 单行损坏不再毁掉整个索引。

### 6.2 SQLite 化实测（2026-10-18）→ 退化，已回退

动机是「增量并入只写变化的行」。正确性全部验证通过，但实测是退化：

| 指标 | 24.9 万条 / 12 base（20.7k/base） | 75 万条 / 12 base（62.5k/base） |
|---|---|---|
| ① 启动加载 `load()` | JSONL **673ms** ／ SQLite 1.09s ⇒ **0.62×** | JSONL **2.37s** ／ SQLite 4.71s ⇒ **0.50×** |
| ② 单游戏增量写（改 1 条） | JSONL 35.1ms ／ SQLite **28.7ms** ⇒ 1.22× | JSONL 242ms ／ SQLite **212ms** ⇒ 1.14× |
| ③ 全库增量写（各改 1 条） | JSONL **353ms** ／ SQLite 385ms ⇒ 0.92× | JSONL **2.47s** ／ SQLite 2.55s ⇒ 0.97× |
| ④ 落盘体积 | JSONL 48.5MB ／ SQLite 56.5MB + WAL 20.9MB | JSONL 146.7MB ／ SQLite 187.4MB + WAL 31.3MB |

复跑（任何机器可跑，不需要真实索引）：

```bash
node scripts/bench-index-store.cjs --synthetic 83000  --bases 12 --iters 5   # ≈24.9 万条
node scripts/bench-index-store.cjs --synthetic 250000 --bases 12 --iters 3   # ≈75 万条
node scripts/bench-index-store.cjs --dir json/index --iters 5                # 真实索引（只读，先复制）
```

**读法**：写入看 `min`/`p50`；`avg` 会被 WAL 自动 checkpoint 的尖峰带偏
（实测同一操作 min 109ms、avg 666ms）。

### 6.3 根因

1. **成本在序列化，不在文件写**：调用方每次传**全量 records**，`mapToRecords` + 逐条 `JSON.stringify`
   是两份后端都要付的固定成本；JSONL 的「写整个文件」落到页缓存近乎免费，
   SQLite 省下的 I/O 抵不过它新增的「行 → 对象」反序列化
2. **载入更贵**：`readIndex` 从库读要物化行对象 + 逐行 `JSON.parse`，JSONL 只是切行 + `JSON.parse`；
   而启动加载是**每次启动都付**的固定成本 ⇒ 这一项退化的权重最高
3. **体积更大**：行里存的是值 JSON 文本，外加 `(base, sec, k)` 主键索引；WAL 是额外开销

### 6.4 与「下载任务列表」对比（同样换库，结论相反）

| | 下载任务列表 | 反查索引 |
|---|---|---|
| 数据规模 | 万级（峰值 3.6 万项） | 十万级（24.7 万条 / 76.9MB） |
| 写入形态 | **小而频繁**（每个文件状态变化都落盘） | **大而整份**（每游戏文件整体重写） |
| 载入权重 | 可忽略 | **每次启动全量载入，权重最高** |
| 实测 | 增量落盘 134ms → **30ms（4.5×）** | 启动加载 **慢 1.6–2×**，写入打平 |
| 结论 | **划算** | **不划算，回退** |

⇒ 判据：**「写入频繁且单次小、载入不重要」才适合换库**；「整份重写 + 启动全量载入」不适合。

### 6.5 现状

- 默认 **JSONL 优先**
- SQLite 后端保留但需显式开启：`GBMD_INDEX_BACKEND=sqlite`（且 `node:sqlite` 可用）
- 回退点集中在 `index-store.js`：`sqliteEnabled()` + `readIndex` / `writeIndexAtomic` / `listBases` 的读取顺序

## 七、后续可做的写放大优化（方向已定，未实施）

要做到「只写变化的行」，必须**改接口层**而不是换存储后端：

1. 让 `saveGameFile` / `ingestModDir` 只把**变化的 key**（`{sec, k, v}` 列表）交给存储层，
   避开全量 `mapToRecords` + 全量 `stringify`
2. 存储层按 key 增量落盘（JSONL 用「追加 + 定期压缩」，或 SQLite 只 UPSERT 传入的 key）
3. 验收口径：用 `scripts/bench-index-store.cjs` 同一口径复测，且
   `test/hash-index-baseline.test.cjs` 的逐字段等价基线必须保持通过

## 十、运维与排查

- `json/index/` 整目录在 `.gitignore` 中，索引**不入库**
- **残留 `index.db`**：默认读路径是文件优先，所以残留库文件**不会被读到**；确认无用后可移入 `.trash`
- 常见现象与判断：
  - **启动后搜索无结果** → ① 索引目录为空 ② `.jsonl` 坏行过多（看返回的 `badLines`）③ 迁移失败（看启动日志告警）
  - **磁盘持续增长** → 追加产生同键重复行；载入时若重复行超过实时键数 1.5 倍会**自动压缩**一次（用内存 Map 全量重写，结果与原实现逐键一致）
  - **想回退某个迁移** → 从 `json/index/.trash/<时间戳>-<原名>` 移回
- 部署端做格式变更前，建议整目录打包到 `json/.trash/pre-<变更>-<时间戳>.tar.gz`（历史做法）

## 十一、已知边界

- 追加会产生同键重复行（重下/更新同一 mod）；>1.5× 自动压缩
- 本体系**不含**查询/搜索逻辑，也不含在线搜索
- 索引**没有对外导出端点**（只在服务端落盘与查询）；导出/导入统一为 JSONL 的是**搜索记录**，属另一条链路
- 游戏名做文件名依赖 `sanitizeGameName()`；跨平台（含中文、冒号）已由测试覆盖
